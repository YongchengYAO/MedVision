# Dependencies of the CPU stages (2, 3, 4), shared by EVERY judge reader.
# Installed by setup_judge_env.sh into whichever venv it builds.
#
# Why a separate file. These have nothing to do with which model does the reading:
# the driver runs Stage 1 (GPU) and Stages 2-4 (CPU) under the SAME `PYTHON`, and
# Stages 2-4 import `medvision_bm` so that judge-parsed samples are scored by the
# same code that produced the published numbers. That chain is identical for every
# reader, so a copy per reader would be two copies of one fact.
#
# Why the list is this long. Stage 3 imports the task summarizers, which import
# `medvision_utils`, which imports `lmms_eval.tasks`, whose `__init__` imports
# `lmms_eval.utils` -- the whole evaluation harness. Measured 2026-08-15: the CPU
# stages load 90 third-party top-level modules. Nothing in Stage 1 touches them, so
# a judge env without them builds cleanly, passes verification, runs a thirteen-hour
# GPU sweep and dies on Stage 2/3 -- which is why run_llm_parsing.sh now probes the
# real summarizer import before the sweep instead of after it.
#
# WHY NOT JUST INSTALL lmms_eval's OWN DEPENDENCIES. Its pyproject.toml declares
# `torch>=2.1.0,<2.8`. The judge environment runs torch 2.10.0
# (gemma-4), so installing that dependency set would DOWNGRADE torch and break vLLM
# -- trading a missing-module error for an ABI crash. This list is therefore the
# MEASURED import set, not the declared one, and deliberately contains no
# torch/transformers/vllm pin.
#
# Regenerate after changing what Stages 2-4 import:
#   python -c "import sys; before=set(sys.modules); \
#              import medvision_bm.benchmark.summarize_TL_task; \
#              print(sorted({m.split('.')[0] for m in set(sys.modules)-before}))"
# run under an interpreter that HAS the eval stack, then diff against the judge env.
#
# Unpinned on purpose: none of these interact with the vllm/transformers pins the
# reader environments fight over, so a version constraint here would add a thing to
# resolve without buying anything.

# --- medvision_ds benchmark plans, imported LAZILY at run time -----------

# parse_utils.get_targetLabel_imgModality_from_biometry_benchmark_plan resolves a
# per-dataset plan module with importlib.import_module WHILE processing records, so
# the dependency only materialises partway through Stage 3 -- and then arrives
# wrapped as `ValueError: Error loading benchmark plan for <dataset>`, which reads
# like corrupt data rather than a missing package.
#

# these are what those two reach and the judge envs lacked. The rest of
