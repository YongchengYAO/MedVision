# Troubleshooting: RFT data building, the verl fork, and RFT-model evaluation

Format: symptom / error fragment -> likely cause -> fix + how to validate -> when to stop. Cross-cutting issues
(install pins, dataset download, env vars) live in `../../../references/troubleshooting.md`.

## Parquet building

| Symptom | Likely cause | Fix / validation | Stop when |
| --- | --- | --- | --- |
| Builder killed with no traceback (exit 137 / "Killed") while formatting a large (e.g. 1M-row) detection set; RAM climbs steadily | `build_parquet_ds` holds the whole formatted split in RAM; each format worker buffers 50 PIL images (~0.75 MB at 512x512) and the Arrow table grows to ~100 KB/row | Use the checkpointed builder (`scripts/build_parquet_ds.sh --checkpointed`) and lower `--shard-size` / `--workers-format` (32 GB box: `--workers-format 16 --shard-size 20000`); rerun the same command to resume from `checkpoint.json`; set `PYTHONFAULTHANDLER=1` (the wrapper does). Check the **cgroup** memory limit, not `free -g`. Validate with `scripts/inspect_parquet_ds.py --path <dir>` (shards done / merged) | the container limit is below ~4 GB or disk cannot hold ~2x100 GB for 1M rows |
| `AssertionError: [Error] MedVision_DATA_DIR environment variable must be set.` | the builders read the env var in `load_split_limit_dataset`; `--data_dir` does not export it | `export MedVision_DATA_DIR=<data_dir>` (the wrapper does this) | -- |
| Loader fails about `MedVision_PLANNER_VERSION` / release acknowledgement | `medvision_ds` >= 1.1.0 requires the annotation version; pinning below the latest also needs `MedVision_ACK_RELEASE` | `export MedVision_PLANNER_VERSION=1.0.0` (paper data) and, if below latest, `MedVision_ACK_RELEASE=<latest>`; see `../../dataset-and-tasks/SKILL.md`. Note T/L sample sets differ across versions | -- |
| `ValueError: [Error] <model_family_name> is not recognised/supported.` from `get_resized_img_shape`, or a failure or the T/L / A/D text formatter right after loading | `--model_family_name` is not one of the hard-coded keys (`qwen25vl`, `qwen3vl`, `gemma3`, `gemma4`, `medgemma`, `lingshu`, `llama_3_2_vision`, `llava_onevision`, `internvl3`, `minimax_m3`, `glm4v`, `meddr`, `llava_med`, `huatuogpt_vision`, `healthgpt`, or the `vllm_*` variants) | pick the key of the family you will RFT; `--model_hf` must be a checkpoint of that family (its image processor is loaded). Detection-only builds never call the probe, so a wrong key surfaces only with `--tasks_list_json_path_TL/_AD` | adding a family needs the maintainer path (`../../extending-models-and-tasks/SKILL.md`) |
| A parquet built with `model_family_name=qwen25vl` (512x512) is used to RFT a Gemma-4 (or any other family) model; T/L and A/D rewards stay low / training "learns" wrong scale | the `Additional information:` block states the image size and pixel size **as perceived by Qwen2.5-VL** (multiple-of-28 resize, 512 -> 504); Gemma-4's processor perceives a different canvas, so the stated pixel size is wrong for every measurement sample. Detection rows are unaffected (relative coordinates, no pixel size) | rebuild with `--model-family gemma4 --model-hf <gemma4 checkpoint>` (output under `verl_datasets/gemma4/`); keep the `qwen25vl` set only for Qwen2.5-VL-family models. Validate by reading the first T/L prompt with `inspect_parquet_ds.py` and comparing the stated size with the target processor's output | -- |
| Validation split has 100 rows per task although you asked for fewer / more | `--val_sample_limit_task_*` <= 0 falls back to `--val_sample_limit_per_task` (default 100); the resolved value must be > 0 (asserted) | set the task-specific val flags explicitly; the global `--val_sample_limit` then caps (or oversamples with replacement) the concatenated set | -- |
| Training set is smaller than the per-task sum, or contains duplicates | `--train_sample_limit` (global) is applied **after** concatenation: smaller than the sum -> seeded shuffle + head (silent truncation); larger -> `np.random.choice(replace=True)` | keep the global cap equal to the sum of per-task caps (the wrapper defaults to the sum and warns on mismatch); `-1` disables it | -- |
| `ValueError: ... =0 is ambiguous: use -1 (or leave it unset) for no limit; to skip a task, omit its --tasks_list_json_path_* instead.` | a sample limit of 0 | omit the task's JSON path to skip it | -- |
| `ValueError: No task JSON paths provided. At least one of --tasks_list_json_path_detect / _AD / _TL must be set.` (checkpointed builder) | no task list given | pass at least one `--tasks_list_json_path_*` | -- |
| Task names not found / wrong configs loaded | eval-namespace task list (`tasks_MedVision-*-CoT.json`, `BoxCoordinate`) passed instead of the SFT lists (`*__train_SFT.json` with `BoxSize` / `TumorLesionSize` / `BiometricsFromLandmarks` keys); the loader maps eval-side `BoxCoordinate` names to `BoxSize` configs only for detection | use `tasks_MedVision-{AD,TL,detect}__train_SFT.json`; namespace rules in `../../dataset-and-tasks/SKILL.md` | -- |
| Output directory name shows `-1` / `all-1` or a different name than expected | per-task limit `-1` (whole pool) and/or global `-1` are printed literally; absent tasks print `0` | this is the convention (`ds__AD<a>_D<d>_TL<t>_all<total>...`); the fork recipes expect the exact names listed in `rft-recipes.md` §5 -- match the limits, do not rename | -- |
| Resume rebuilds everything | any change of limits, resize or `--without_cot_instruction` changes the directory name (new dataset); `--out-dir` in the wrapper moves the finished directory away from `checkpoint.json`'s location | rerun with identical flags; only move finished builds | -- |
| `FileNotFoundError: Cannot merge: N shard(s) missing` | a shard file was deleted after being recorded in `checkpoint.json` | remove its index from `completed_train_shards` in `checkpoint.json` (or delete the file's entry) and rerun to regenerate it | -- |
| Very slow first build / network errors | first build downloads the MedVision datasets named in the task lists (`--ds_download_mode reuse_dataset_if_exists` reuses local copies afterwards) | download first via `../../dataset-and-tasks/SKILL.md`; `force_redownload` only on purpose | no network access |
| `--without_cot_instruction` set and the fork's process reward is always 0 / NaN | lite rows carry `extra_info={"placeholder": true}` (T/L) or only `metric_type` (A/D): no landmark ground truth | rebuild without the flag (paper setting; the flag is marked deprecated in source) | -- |
| Older `medvision_bm` crashes with `ValueError: too many values to unpack` in `_format_data_DetectionTask_verl` | pre-fix bug in the no-CoT detection formatter (the text formatter returns a single string) | upgrade `medvision_bm`; current source builds `extra_info` from the target (covered by the repository's CPU unit test) | -- |
| `--prepared_ds_dir` / `--dataloader_num_workers` have no effect | parsed but unused by all builders | rely on the canonical output path; ignore the flags | -- |

## verl fork (GRPO training)

| Symptom | Likely cause | Fix / validation | Stop when |
| --- | --- | --- | --- |
| Recipe exits immediately: `Set DATASET_ROOT ...` / `Set BASE_MODEL_PATH ... or BASE_MODEL_HF ...` / `set only one of BASE_MODEL_PATH and BASE_MODEL_HF` | required env vars missing or both base-model variables set | export `DATASET_ROOT` (the parquet dir) and exactly one of the two; preview with `DRY_RUN=1` | -- |
| vLLM rollout crashes with a CUDA device-side assert after a transient Hub error; "processor failed to load" | a Hub id was given directly as `actor_rollout_ref.model.path`: ~15 Ray/vLLM workers download concurrently | always pass a Hub id through `BASE_MODEL_HF` (the recipe downloads to `models/<name>` first) or a local dir via `BASE_MODEL_PATH` | -- |
| Curriculum never promotes samples / errors about missing `answer_error` | `+reward_model.use_reward_loop=True` missing (only the async reward loop propagates per-sample `answer_error`); or `task_key`/`task_group_map` do not match the parquet's `ability` values | keep the recipe's reward-loop flag and `task_key=ability`, `task_group_map='medvision-angle:AD,medvision-distance:AD'`; options: fork `CURRICULUM_FILTERING.md`, `REWARDS.md` | -- |
| Reward is always `r_format` only (process/answer 0) | wrong `reward_kwargs` (`format_reward`, `composition`, `reward_mapping_func`), or rows lack `extra_info` landmarks (lite build), or the `ability` column was changed | verify `custom_reward_function.path/name` and `+custom_reward_function.reward_kwargs.*` as in `rft-recipes.md` §2; inspect the parquet's `ability` / `extra_info` | -- |
| Private repo error for `YongchengYAO/MedVision-V0-7B-dev0630` | the multitask recipes default `BASE_MODEL_HF` to the paper's private full-SFT checkpoint | set `BASE_MODEL_HF=YongchengYAO/MedVision-V0-7B` (public) or `BASE_MODEL_PATH=<your SFT checkpoint>` | you need the exact private base |
| Merged model keys start with `base_model.model.` and fail to load | LoRA training in verl leaves PEFT wrapper prefixes | `python -m medvision_bm.rft.verl.patch_layer_name --model_dir <merged_dir>` (patches safetensors + index in place) | -- |
| A decaying LR does not reach zero with the curriculum on | epochs shrink but the schedule horizon is fixed from epoch 1 (fork limitation) | use a constant LR (paper recipes) | -- |

## Evaluating the trained model

| Symptom | Likely cause | Fix / validation | Stop when |
| --- | --- | --- | --- |
| Pinned eval stack (`transformers==4.54.1`, `vllm==0.10.0`) cannot read the merged checkpoint's `config.json` / processor (nested Qwen2.5-VL config keys, unknown fields) | the merge ran under transformers 5.x, which writes nested Qwen2.5-VL configs; the fork pins `transformers<5` for this reason | re-run `python -m verl.model_merger merge ...` in an env with `transformers<5`; weights are fine. **Unverified community note:** some users restore the `config.json` / processor files from the checkpoint's `actor/huggingface/` directory instead of re-merging -- check the files exist before relying on this | -- |
| RFT model outputs lack `<think>` / `<answer>` structure at eval time; SR drops | `--use_system_prompt` omitted (the model was trained with `rft_prompts.SYSTEM_PROMPT` as the system message) | add `--use_system_prompt` (and `--log-sys-prompt` to record it) | -- |
| T/L and A/D metrics far worse than validation rewards suggested | `--reshape_image_hw` missing or different from the training resize (`512x512` for MedVision-V0); or evaluating with a different `MedVision_PLANNER_VERSION` than the paper's `1.0.0` | pass `--reshape_image_hw 512x512`; export `MedVision_PLANNER_VERSION='1.0.0'` to reproduce the paper | -- |
| `eval__medvision-model-rft` starts installing packages / downgrades torch | run without `--skip_env_setup` (installs hub 0.35.3, vendored lmms_eval `qwen2_5_vl`, medvision_ds, torch cu124, vllm 0.10.0, transformers 4.54.1) | prepare the env once (`install_vendored_lmms_eval --lmms_eval_opt_deps medvision_v0`, `requirements_eval_medvision-v0.txt --no-deps`) and pass `--skip_env_setup`; `../../environment-setup/SKILL.md` | -- |
| Task skipped: `Task ... already completed. Skipping...` | the completed-tasks JSON already lists it for this `--model_name` | use a new `--model_name` or edit / remove the entry; `--skip_update_status` for debugging | -- |
| No GPU / `CUDA` errors | evaluation needs vLLM on CUDA (tensor parallel = visible GPUs) | stop; document the command | always on CPU hosts |
