# Troubleshooting the LLM-judge parsing pipeline

Symptom → cause → fix → when to stop. Error fragments are quoted from the
pipeline's own sources. Cross-cutting failures (installs, dataset downloads,
evaluation) are in `../../../references/troubleshooting.md`.

First move for almost everything below:

```bash
python scripts/check_judge_env.py --python "$PYTHON" --repo-root <repo>
```

---

## 1. `PYTHON` unset — the wrong interpreter runs

**Symptom.** The banner says "PYTHON unset". Then one of:
`Stage 1 cannot import vllm under /usr/bin/python3`,
`Stage 1 needs a GPU and this interpreter cannot use one`, or
`ERROR: could not query CUDA through <PY>` — on a pod that visibly has GPUs.

**Cause.** `PYTHON` defaults to the first `python3` on `PATH`. A GPU pod usually
has several, and the one that wins is rarely the judge env. The judge needs a
**newer vLLM than the evaluation code pins**, so the evaluation interpreter is
the wrong one even when it has a vLLM.

**Fix.**

```bash
export PYTHON=<judge-env>/bin/python
python scripts/check_judge_env.py --python "$PYTHON" --repo-root <repo>
```

`check_judge_env.py` exits 1 when vllm is missing, 2 on a version mismatch, 0
when the interpreter is usable (a missing GPU is a warning: the CPU steps work).
Never `pip install vllm` into whatever interpreter happened to run — the driver
deliberately refuses to suggest that.

**When to stop.** If no judge env exists, building one downloads several GB and
needs Python 3.10–3.12 (`judge-environment.md` §2). If the pod has no GPU at all,
`prep`/`stage0`/`analyze` still work; `smoke`/`pilot`/`full` do not — move to a
GPU pod rather than forcing `SKIP_GPU_CHECK=1`.

## 2. vLLM version mismatch between the evaluation env and the judge env

**Symptom.** `check_judge_env.py` prints
`MISMATCH (installed 0.11.0, registry pins 0.19.0)` and exits 2. Or an
undefined-symbol crash at `import vllm`. Or the reader loads but produces
different verdicts than a colleague's run.

**Cause.** The repository's per-model evaluation requirements pin vLLM 0.10.x /
0.11.0 for most wrappers; the judge registry pins `vllm==0.19.0` and Gemma-4
needs a Transformers 5.x line that a vLLM declaring `transformers<5` cannot host.
The two stacks are mutually exclusive in one environment.

**Fix.** Keep them in **separate** virtual environments; never install judge
requirements into an evaluation env or vice versa
(`../../environment-setup/SKILL.md`). Rebuild the judge env from the pinned
requirements. The undefined-symbol crash specifically is the nccl override: torch
2.10.0 calls `ncclCommShrink`, absent from the `nvidia-nccl-cu12` release that
torch's metadata pins with `==`, so the second requirements pass overrides it.

**When to stop.** Do not "fix" the red `incompatible` block the second pip pass
prints — those are declared bounds, not observed failures. The gate is the setup
script's own verification line
(`...and all of them import cleanly, so those bounds are conservative.`). If a
package genuinely fails to import, stop and report it; do not hand-downgrade.

## 3. `prep` deleted / archived something you wanted

**Symptom.** A finished `judge-out_<T>_<reader>.jsonl` is now `.v1`; the queues
are gone; with `--fresh`, `llm-parsed_<reader>*/` directories are gone too.

**Cause.** `prep` is the **only destructive step** and it runs by default when no
step list is given. `--fresh` widens it to delete the reader's re-parsed record
directories.

**Fix.** Judge answers are archived, not deleted: move the `.v1` file back to its
original name **before** the judging step and the run resumes from where the
previous one stopped (rows are matched by identity). Queues are pure derived data
— `stage0` rebuilds them (~1.1 GB, minutes of CPU). `llm-parsed*/` directories
are regenerated by `analyze` from the judge-out file.

**Prevention.** Name your steps: `stage0 full analyze` for a resume or a
re-pointed tree; `prep` only when retiring a previous campaign. `prep` is scoped
to `TASKS` and to the selected reader, so narrow both.

**When to stop.** If `--fresh` deleted records **and** the judge-out archives were
already consumed and removed, the only recovery is a full re-judge (GPU hours).
Say so rather than improvising.

## 4. `prompt_fp` mismatch — queues are locked

**Symptom.**

```
[stage1] ABORT the queue was built for a different prompt.
    step_key='TL': queue has 'c515f64a54eafab8', current prompt is '…'
```

or

```
[stage1] ABORT <out> holds N row(s) written under a different prompt, or by a
  different judge model (including the --mock stand-in).
```

**Cause.** Every queue row and judge-out row carries `prompt_fp`, a hash over the
**rendered** prompt (system + user template + output skeleton + JSON schema), the
response-window constants, the elision marker, the task's `max_tokens` and the
reasoning-effort setting. Editing any of those — including `--max_tokens` on the
command line — moves the stamp. Reader identity is deliberately **not** in it, so
a new reader reuses the queues.

**Fix.** Decide which is true:

- *You meant to change the prompt/budget.* Rebuild: `stage0` (~1.1 GB of queues)
  and re-judge; the old judge-out rows answer a different question and must not
  be mixed in. Use `--fresh`.
- *You did not.* Revert the edit and re-run; the stamps come back.
- *You are running a legitimate repair whose rows span two stamps.* Whitelist the
  historical stamp with `--accept_prompt_fp <stamp>` (driver: `ACCEPT_FP`);
  the stamp of the rows on disk is printed in the abort message. Pair it with
  `--redo_invalid` (recipe 6 in `recipes.md`).

**When to stop.** Do not raise `max_tokens` above the shared 4096 budget to
"fix" truncation: it forces a fingerprint rebuild and buys nothing (Detection's
real requirement is p99 = 435 tokens; what hits a cap is overwhelmingly
degenerate repetition). Do not hand-edit `prompt_fp` values in a JSONL.

## 5. Roster / config mismatch

**Symptom.**

```
[GATE FAIL] 2 roster model(s) could not be resolved under Results/<tree>:
    <model dir>  --  no such directory
    <model dir>  --  no sample files in parsed/
```

**Cause.** The roster YAML key must be the model's **directory name** under that
Results tree, and the directory must already contain `parsed/*.jsonl`. There is
no glob fallback: a typo, a display name used as the key, or a tree that has not
been through `parse_outputs` all land here. The value (display label) is free
text and never resolved, so a typo there is silent — it just prints wrong.

**Fix.** Generate the roster from the tree instead of typing it:

```bash
python scripts/make_roster_yaml.py --results-dir <repo>/Results/<tree> --dry-run
```

It skips exactly what Stage 0 would reject (files, `judge-*`, `summary_*`,
`llm-parsed*`, `_archive*`, hidden entries, directories without
`parsed/*.jsonl`). Fix the roster or run step 2 of
`../../results-parsing-and-metrics/SKILL.md` first.

**Note.** A failed Stage 0 gate **retracts** the queue it had already written, so
there is nothing half-built for Stage 1 to consume. That is intentional.

**When to stop.** If a model has no `parsed/` because it has no evaluation
outputs at all, this is an evaluation problem, not a judge problem
(`../../benchmark-evaluation/SKILL.md`).

## 6. OOD (or any non-default) tree judged against the wrong roster

**Symptom.** An OOD split reports the main campaign's models, or Stage 0 fails
its roster gate on an OOD tree, or two splits' artifacts appear in one tree.

**Cause.** `TASK_DIR_<task>` and `ROSTER_YAML_<task>` are **independent**
overrides. Setting only the tree keeps the default roster; setting only the
roster keeps the default tree. Both are per task, and `TASKS` must also be
narrowed or the other two tasks run with their defaults.

**Fix.** Set all three, one invocation per split, sequentially:

```bash
TASKS="TL" \
TASK_DIR_TL=Results/MedVision-TL-v2-CoT-planeOOD \
ROSTER_YAML_TL=script/llm-parsing/config-TL-CoT-planeOOD.yaml \
PYTHON=<judge-env>/bin/python \
bash <repo>/script/llm-parsing/run_llm_parsing.sh stage0 full analyze
```

There is **no wrapper script** for the four splits and there should not be; the
two that once existed were retired in 2026-08-19. See `recipes.md` §3 for the
tree/roster table.

**Side effect to expect.** Stage 3b rewrites each tree's *strict* summary
roster-scoped. A summary that previously included a non-roster model loses that
row until a summarizer is re-run without `--models`.

## 7. `[gate n/a]` on the response-count gate

**Symptom.**

```
[gate n/a] non-default task_dir Results/<tree>; the full-roster count check
           applies only to Results/MedVision-TL-v2-CoT
```

**Cause.** `EXPECTED_ROSTER_COUNTS` (TL 46,379 / AD 39,140 / Detection 437,349
for the 19-model roster) describes the **default trees only**. Any
`TASK_DIR_<task>` override, and any `--limit` build, skips it.

**This is not an error.** It is the correct behaviour: an OOD split with a
3-model roster could never match the main totals, and gating it would make every
re-pointed build abort on numbers that were never a promise about that tree. The
parser-replay gate and the roster-resolution gate still run.

**The inverse is the real failure:**
`[GATE FAIL] response count 44,102 != expected 46,379. Roster resolution is
wrong -- fix before spending GPU time.` on a *default* tree means the roster
changed (or a model's outputs did) and `EXPECTED_ROSTER_COUNTS` was not updated.
Print the new total with
`build_judge_queue.py --task_type <T> --dry_run` and update the constant
deliberately — never to silence the gate.

**When to stop.** If you cannot explain why the total changed, stop and find out;
that gate exists to catch a roster edit before it costs GPU hours.

## 8. GPU OOM / not enough GPUs

**Symptom.**

```
ERROR: NUM_SHARDS=4 x TP=2 = 8 GPUs, but only 4 are visible [0 1 2 3].
       Each shard loads its own copy of gemma-4-31b at
       gpu_memory_utilization=0.90; overlapping them will OOM.
```

or a CUDA OOM once the engine starts, or a sweep that crawls.

**Cause.** Total GPUs used = `NUM_SHARDS × TP`, and the driver checks this
*before* any weights load. The reader is ~62 GB bf16: on one 80 GB card at
`gpu_memory_utilization=0.90` only ~10 GB is left for KV cache, so the sweep runs
with few requests in flight — slow, and an outright OOM on smaller cards. The
driver's default is `TP=1, NUM_SHARDS=1` (one GPU), overriding the registry's
`tensor_parallel=2`.

**Fix.** Use the fewest GPUs per process the weights fit in, and spend the rest
on more processes — shards share nothing and scale near-linearly, while TP adds
an all-reduce per layer and buys **capacity, not speed**:

```bash
GPU_NUM=4 TP=2 bash <repo>/script/llm-parsing/run_llm_parsing.sh   # two 2-GPU processes
GPU_NUM=4      bash <repo>/script/llm-parsing/run_llm_parsing.sh   # four 1-GPU processes
```

`GPU_NUM` must divide by `TP`; an explicit `NUM_SHARDS` wins over it. A
`NOTE: N GPU(s) will sit idle` line means the layout does not use every visible
card. `CUDA_VISIBLE_DEVICES` is honoured and never re-indexed; shard *S* takes
devices `[S·TP, S·TP+TP)` of that list.

**The two-H100 assumption.** The quoted costs — ~30 min `pilot`, ~13 h `full`
over 522,868 responses, ~1 h CPU `analyze` — are for **two H100s**. On one
80 GB card expect substantially longer; on smaller cards `TP` must rise until the
weights fit, at which point fewer shards remain and throughput drops further.
Budget accordingly rather than assuming the published figures.

**When to stop.** If the reader does not fit at any `TP` the pod can supply, stop:
this needs different hardware, not different flags. Also make sure `HF_HOME` has
~62 GB free before the first `smoke` — the weights download on first load.

## 9. Repairing a partial run

**Symptom.** The judge report shows a block of judge-invalid rows; or a sweep was
killed; or `--redo_invalid` seemed to do nothing.

**Cause and fix, in order of cheapness:**

| what actually failed | fix | cost |
|---|---|---|
| the process was killed | just re-run the same step — rows are skipped by `qid`, output is appended in fsynced chunks of 2000 | resumes |
| the reader's JSON could not be *decoded* | `reparse_judge_out.py --in <judge-out> --out <new>` then `analyze` | CPU |
| the reader's answer itself was unusable | `run_judge_vllm.py … --redo_invalid --accept_prompt_fp <stamp>` then `analyze` | GPU, only the bad rows |
| the prompt changed | full re-judge (`--fresh`) | GPU hours |

**The silent no-op.** `--accept_prompt_fp` **without** `--redo_invalid` does
nothing: the bad rows already have a `qid`, so they count as done and are skipped.
Both flags, always.

**Never `cat new old`.** A repair *appends* to the same file and Stage 2 resolves
duplicates per `doc_id` last-wins; concatenating in the other order silently
restores the broken rows. Also note the merge guard: Stage 1 refuses to overwrite
a merged file that holds qids no shard has (i.e. repair rows) or whose
`.<name>.reparsed` marker is at least as new as the file.

**When to stop.** `reparse_judge_out.py` refuses to write if any row moves
ok→invalid or any already-ok row's values change. That refusal is a finding —
investigate the decoder change, do not pass `--allow_regressions` /
`--allow_value_changes` to get past it.

## 10. MOCK numbers reported by mistake

**Symptom.** A report looks plausible but the record invariants fail on
`judge_model='mock'`; or a number was quoted from a run that had `MOCK=1` in the
environment.

**Cause.** `MOCK=1` substitutes a deterministic regex extractor for the reader. It
exercises every gate on a CPU box — that is its only purpose. Three isolation
mechanisms keep mock rows out of real runs: a `.MOCK.jsonl` output filename,
provenance in the resume (a mock row is stale to a real run and vice versa), and
`LLM_judge.judge_model` on every record.

**The gap they do not cover.** Stage 2 under `MOCK=1` writes into the **same**
`llm-parsed_<reader>[-limitN]/` directory a real run uses — there is no MOCK infix
on the directory. A mock `analyze`/`pilot` on a tree holding real records
overwrites them file by file.

**Fix.** Re-run the real `analyze` against the real judge-out file to rewrite the
records; the invariants gate then passes. For future mock exercises point
`TASK_DIR_<task>` at a scratch copy of the tree.

**When to stop.** **Never report a MOCK number** — not as a placeholder, not as
"approximately". The banner says so on every mock run; treat a mock figure that
reached a report as a retraction, not a rounding error.

## 11. The `smoke` gate fails (judge output schema)

**Symptom.**

```
smoke: the judge did not clear --min_valid_rate. Read the printed …
```

or `smoke: a shard failed`, or `smoke: missing <out>.shard<S>`, or
`smoke: missing <queue> -- run stage0 first`.

**Cause.** `smoke` judges 200 evenly spaced rows of the first task in `TASKS` into
a temporary directory and asserts ≥95% of them come back schema-valid **and** that
spans were quoted. The same guard runs inside every Stage-1 process over its first
200 rows (`--min_valid_rate`, default 0.95): if it fails, the run aborts
**writing nothing**, so a broken reader cannot cost thirteen hours.

**Fix.** Read the printed failure reasons. The common ones:

- the wrong weights (a checkpoint that is not the registered reader, or a
  different quantization) — check `JUDGE_MODEL` / `JUDGE_MODEL_HF`;
- a truncated budget, if `--max_tokens` was overridden downward — it shows up as
  `no_json_object` / `json_decode_error`, never as an obvious error;
- a Transformers line the reader cannot load — `check_judge_env.py` reports the
  major version against the registry's expectation.

Missing queue → run `stage0` first. Shard failure → the shard's own abort message
is printed above the summary; read that, not the driver line.

**When to stop.** Do not lower `--min_valid_rate` to get past `smoke` on a
production sweep. A low rate means the reader is not answering in the required
shape, and everything downstream degrades to `undetermined`. (A *repair* queue is
the one legitimate case for a low or zero rate, and that is run by hand.)

## 12. Two runs of the judge disagree

**Symptom.** Re-judging the same rows gives different verdicts; a judge-invalid
rate differs between machines; a "recovery" appears after a code change.

**Cause.** Judge output is **not** reproducible — run to run on the *same* GPU,
not merely across generations — and the cause is numerical non-determinism, not
sampling (`temperature=0.0`, `top_p=1.0`, so the seed is inert). Kernels are not
batch-invariant by default (reduction order depends on batch shape, which depends
on shard layout, chunk boundaries and arrival order), and prefix caching adds a
second path (`enable_prefix_caching=True` is hardcoded; there is no
`--enforce_eager` flag).

**Blast radius.** A flip can cost a *recovery*; it can never corrupt a published
value, because the strict regex has unconditional priority wherever it succeeded.

**Operating rules.**

1. Never compare judge-invalid rates across machines or checkpoints.
2. Never credit a re-run's recovery to a code change without a same-raw A/B
   (`reparse_judge_out.py`) or a same-day control arm.
3. Never sample a probe in roster order — roster order is model-biased (a
   2,000-row roster-ordered probe once suggested 82.9% where the population gave
   63.0%).
4. Treat `judge-out_*.jsonl` as the artifact of record. Re-deriving reports from
   it (Stages 2–4) is byte-reproducible; re-judging is not. **Release the file,
   not a re-run.**

**If determinism is actually required.** The pinned engine (`vllm==0.19.0`) ships
batch-invariant kernels behind `VLLM_BATCH_INVARIANT=1`. Enabling it is not a
single flag: it raises `RuntimeError` at worker init unless the attention backend
is FLASH_ATTN or TRITON_ATTN (the pipeline pins none, so vLLM auto-selects), it
forces single-channel single-thread tree NCCL settings (felt at
`tensor_parallel=2`), and it disables AOT compile and TF32 fast paths. Throughput
cost is expected to be material and is unmeasured. It does **not** invalidate the
queues (engine settings are not in the fingerprint) but does require a re-judge.

**When to stop.** Treat it as what makes a determinism-critical arm *possible*,
not as a production default. Do not quote flip rates measured on the retired
reader for the current one — the current reader's flip rate has never been
measured (its files hold zero twice-judged `(qid, prompt_fp)` pairs).

## 13. `medvision_ds` (or the CPU-stage imports) missing for `analyze`

**Symptom.** One of:

```
medvision_ds is not importable and no checkout was found.
MEDVISION_DS_SRC=<path> contains no medvision_ds/ package.
Stages 2-4 cannot import medvision_bm under <PY>.
```

or, mid-stage, `Error loading benchmark plan for <dataset>` — which reads like
corrupt data and is really a missing package.

**Cause.** Stage 1 and Stages 2–4 need **different** things, and they fail
independently: a judge venv that imports `vllm` perfectly can die on Stage 2's
first line (`datasets`) — after a thirteen-hour sweep. Stage 3 additionally
resolves per-dataset benchmark plans lazily through `medvision_ds`, so that
dependency surfaces partway through the stage.

**Fix.**

```bash
"$PYTHON" -m pip install -r <repo>/script/llm-parsing/requirements-cpu-stages.txt
export MEDVISION_DS_SRC=<path to the medvision_ds source tree>   # if not installed
python scripts/check_judge_env.py --python "$PYTHON" --repo-root <repo>
```

`requirements-cpu-stages.txt` is deliberately **unpinned** and contains no
torch/transformers/vllm — it is not the vendored `lmms_eval`'s declared
dependency set, which pins `torch<2.8` and would downgrade torch under vLLM. Do
not substitute one for the other.

**Why the driver probes both.** Selecting `analyze`/`pilot` makes the CPU probe a
**hard abort**; selecting only `full`/`smoke` makes it a warning, so the sweep can
start while you fix the reporting side. Fix it before the sweep anyway.

**When to stop.** If installing the CPU stage deps would break the vLLM install in
that env, use a second CPU-only interpreter for `analyze` — Stages 2–4 are pure
CPU functions of the judge-out file and can run anywhere `medvision_bm` and
`medvision_ds` import.

## 14. The record-invariants step fails on a directory you did not judge

**Symptom.** `analyze` finishes, then the invariants step reports e.g.
`Detection: strict key removed from every record -- 23,071 records still carry
'filtered_resps'` — while every roster model looks fine.

**Cause.** The invariants test scans **every** `llm-parsed<reader>/` directory
under the tree, roster or not. A stale directory — a copy of `parsed/` renamed,
or a leftover from a retired experiment — fails the check even though the
campaign is correct. (Observed on this repository: one non-roster model directory
whose `llm-parsed_gemma-4-31b/` holds plain strict records with `filtered_resps`
and no `LLM_judge*` keys.)

**Fix.** Identify the offending directory from the failure message, confirm it is
not in the roster YAML, and move it out of the tree (or delete it if it is a
known copy). Re-run the invariants step. Do **not** relax the assertion: an
`llm-parsed*` directory that still carries `filtered_resps` would be summarized
with the wrong key.

**Related.** Pointing a summarizer at such a directory gives
`[FATAL] <file> has no 'LLM_filtered_resps' key.` with the remedy printed —
`--resps_key LLM_filtered_resps`, or drop `--parsed_dirname` to summarize
`parsed/`.

## 15. `prep declined -- nothing changed` in an unattended run

**Symptom.** A cron / `nohup` / CI run stops immediately with that message.

**Cause.** `prep` reads its confirmation from the terminal (`/dev/tty`). With no
terminal the read fails and `prep` **auto-declines**, which stops the whole run.
Redirecting stdin does not help.

**Fix.** Pass `--yes` (short `-y`) or set `YES=1`. Better: name the steps you
actually want (`stage0 full analyze`) so `prep` never runs unattended — a
destructive step behind an auto-declining prompt is the safe default, not a bug.

---

## 16. `Can't load the configuration of 'google/gemma-4-31B-it'`

**Symptom.** Looks like a gated or missing model.

**Cause.** Usually a **trailing newline** in `HF_TOKEN` (or
`HUGGING_FACE_HUB_TOKEN` / `HUGGINGFACE_TOKEN`), which makes the Authorization
header invalid. Newlines in `HF_HOME` / `HF_HUB_CACHE` cause the neighbouring
class of failure.

**Fix.** The pipeline's sourced environment helper strips whitespace from all
three token variables and newlines from the two cache variables, so run through
the driver rather than invoking a stage by hand with a hand-exported token. If
you must export one yourself, strip it (`tr -d '[:space:]'`). Also confirm
`HF_HOME` has ~62 GB free.

**When to stop.** If the token is genuinely unauthorized for the weights, that is
an access problem — stop and ask for access rather than retrying.
